# Как устроен пилот parameter server

Пилот проверяет синхронное обучение на CPU, взаимодействие акторов и обычных
Ray-задач, сбор журнала и возможность независимой проверки результата.
Восстановление обучения после сбоя в этом примере ещё не реализовано.
Стратегии и эксперименты описаны в [постановке](../nis/project.md)
и [плане](../nis/experiment-plan.md).

## Файлы

| Файл | Назначение |
| --- | --- |
| [`ray_ps/model.py`](../ray_ps/model.py) | ConvNet, настройки CPU, копирование и хеширование весов и momentum |
| [`ray_ps/pilot.py`](../ray_ps/pilot.py) | DataShard, вычислительная задача, ParameterServer и координатор |
| [`ray_ps/verify.py`](../ray_ps/verify.py) | Последовательный эталон и проверка журналов/состояния |
| [`ray_ps/check_results.py`](../ray_ps/check_results.py) | Сравнение повторных запусков и проверка обнаружения повреждённого momentum |
| [`examples/recovery_probe.py`](../examples/recovery_probe.py) | Короткая проверка доступности метрик восстановления на счётчике |
| [`tests/test_pilot_verification.py`](../tests/test_pilot_verification.py) | Отказ проверки при пропусках, дублях и неверных входах |

## Один шаг

1. `DataShard.reserve(step)` резервирует конкретные индексы изображений.
   Источники делят MNIST на непересекающиеся части и помнят свои позиции.
2. Координатор помещает текущие веса в объектное хранилище через `ray.put`.
3. `compute_gradient.remote(...)` получает веса, читает назначенный батч
   у актора данных и делает forward/backward. PyTorch вычисляет градиенты.
4. `ParameterServer.apply(...)` проверяет версии и номера источников,
   усредняет градиенты и делает один шаг SGD с momentum.
5. `DataShard.commit(step)` продвигает позиции данных. Координатор записывает
   ID, батчи, задержку и контрольную сумму новых весов.

Один глобальный шаг включает два батча по 32 изображения по умолчанию.
Начальные веса и порядок данных зависят от явно заданного seed.
PyTorch работает на CPU в один поток в каждом процессе.

`DataShard` допускает повтор reserve/commit с текущим ID в пределах жизни
процесса. Это не долговечная защита от дублей после сбоя.
Перезапуски акторов и повторы вычислений в пилоте отключены явно.
`ParameterServer.apply` отвергает неожиданный номер шага; протокол ответа
на повтор уже подтверждённого обновления будет частью восстановления.

## Запуск

Сначала подготовьте Python 3.12 и назначенную ревизию Ray по
[инструкции среды](../nis/environment.md), затем установите ML-зависимости:

```bash
python -m pip install -r requirements-ml.txt
python -m ray_ps.pilot --steps 20 --workers 2 --batch-size 32 --output runs/ps-01
python -m ray_ps.verify --run-dir runs/ps-01
python -m unittest discover -s tests -v
```

Все команды выполняются в корне репозитория. Первый запуск скачивает MNIST
в `runs/data/`. Каталог `--output` должен быть новым: результаты не затираются.
По умолчанию программа отказывается запускаться на другом SHA Ray.
Флаг `--allow-other-ray` предназначен только для разработки, фактический SHA
всё равно сохраняется. Такой запуск не считается проверкой назначенной версии.

Для повторного опыта с теми же параметрами используйте другой каталог,
например `runs/ps-02`. Разные seed или число шагов задаются отдельными
параметрами; это другая конфигурация опыта.

Проверка совпадения двух запусков и обнаружения ошибочного состояния:

```bash
python -m ray_ps.check_results --first runs/ps-01 --second runs/ps-02 --output runs/pilot-checks.json
```

Она сравнивает тензоры побитово и проверяет, что изменение momentum
в отдельной временной копии приводит к отказу проверки.

## Что читать в результате

- `config.json`: параметры, версии библиотек, seed и хеш исходных данных.
- `steps.jsonl`: по строке на шаг; индексы входов, ID/версии, исходы вычислений,
  позиции источников, времена отправления/подтверждения и хеш весов.
- `summary.json`: описательные показатели пилота, включая p95/p99.
- `final-state.pt`: веса, momentum, номер шага и позиции источников.
- `verification.json`: результат отдельной проверки, численные ошибки и допуски.

`completed_pending_independent_verification` в summary означает только
завершение программы. Корректность подтверждает отдельный `verification.json`.
Все 20 шагов пилота включены в p95/p99, включая старт вычислительных процессов.
Это демонстрация доступности данных, не итоговый результат производительности.

Эталон заново строит входы по конфигурации, объединяет батчи и делает обычный
последовательный backward. Он не использует DataShard, ParameterServer и код
усреднения пилота. Сравниваются веса и momentum с `atol=1e-6`, `rtol=1e-5`,
ID и позиции — точно. Общая архитектура модели и PyTorch остаются общей
зависимостью двух реализаций. Для чтения состояния используется
`torch.load(..., weights_only=True)`.

## Проверка метрик сбоя на счётчике

```bash
python -m examples.recovery_probe --mode restart --output runs/probe-restart.json
python -m examples.recovery_probe --mode checkpoint --output runs/probe-checkpoint.json
```

По умолчанию выполняются 8 подтверждённых прибавлений, управляемый сбой
и ещё 8 прибавлений. Ожидается итог 8 в режиме restart и 16 при checkpoint.
Оба отчёта имеют `status: passed`, если подтверждено именно ожидаемое поведение;
в restart это включает потерю восьми ранее подтверждённых эффектов.

Журнал показывает времена запроса сбоя, наблюдения ошибки, готовности
и первой подтверждённой операции. Время восстановления отсчитывается от
запроса сбоя, а не от неизвестного точного момента смерти процесса.
Длительность increment измеряется отдельно и не включает ожидание готовности.
Проба не исследует незавершённое прибавление, replay и неопределённый ответ.
