# Сборка назначенной ревизии Ray на macOS ARM64

Для проекта закреплён коммит Ray
`2ff4d94078ee94b3c9e6e4552ad84f78bad7f75f`. На macOS ARM64 его можно собрать
нативно из исходников. Linux и виртуальная машина для этого пути не нужны.

## Подготовка

Нужны:

- Mac с процессором Apple Silicon, работающий в нативном режиме arm64;
- нативный Python 3.12 с `venv` и `pip`;
- Xcode Command Line Tools: при отсутствии установить командой
  `xcode-select --install`;
- Git, curl, интернет для исходников и зависимостей;
- свободное место для исходников, Bazel, зависимостей и объектных файлов.

При проверке использовались macOS 15.7.9, Python 3.12.11, Apple clang 17.0.0,
12 логических CPU и 36 GiB RAM. Эти ресурсы описывают проверенную машину,
а не установленный минимальный порог сборки. Полный Xcode.app не использовался.

Из корня репозитория:

```bash
bash scripts/build_ray_macos.sh
```

Если Python 3.12 находится вне `PATH`:

```bash
PYTHON_BIN=/path/to/python3.12 bash scripts/build_ray_macos.sh
```

На машине с меньшим объёмом ресурсов можно ограничить параллелизм и память:

```bash
RAY_BUILD_JOBS=4 RAY_BUILD_MEMORY_MB=8192 bash scripts/build_ray_macos.sh
```

Скрипт не устанавливает системные пакеты и не меняет существующую `.venv`.
Он создаёт отдельную среду `work/venvs/ray-pinned`, скачивает Bazel 7.5.0,
проверяет его SHA-256, получает точную ревизию Ray, собирает wheel,
устанавливает его и проверяет `ray.__commit__` и `pip check`.

Версии Python-инструментов сборки закреплены в скрипте:
pip 26.2.2, setuptools 84.2.1, wheel 0.48.0, Cython 3.3.0 и NumPy 2.5.4.
Часть Python-зависимостей upstream Ray разрешается во время сборки/установки;
получившийся состав среды записывается в
`work/setup/ray-pinned-macos-freeze.txt`. Побитовое совпадение повторных сборок
не предполагается.

## Размещение файлов и параметры

Bazel 7.5.0 при проверке не смог запуститься из каталога с кириллицей:
в сообщении об ошибке путь превращался в `???`. Поэтому скрипт создаёт
физический каталог с ASCII-именем в `/private/tmp` и размещает там исходники
и кэш. Python во время сборки вызывается через ASCII-ссылку на среду в `work/`.
Обычная работа с установленным Ray из каталога проекта с кириллицей проверена.

Для повторного использования сборочного дерева можно явно указать путь:

```bash
RAY_BUILD_ROOT=/private/tmp/nis2-ray-build bash scripts/build_ray_macos.sh
```

Этот путь должен быть ASCII, без пробелов. Если в нём уже есть исходники,
скрипт проверит SHA и отклонит посторонние изменения. Он не выполняет
`git reset --hard` или очистку чужой рабочей копии.

Результаты:

| Путь | Содержание |
|---|---|
| `work/build/wheels/` | Собранный wheel |
| `work/venvs/ray-pinned/` | Отдельная установленная среда |
| `work/setup/build-logs/build-ray-macos.log` | Лог компиляции и упаковки |
| `work/setup/ray-pinned-macos-build.json` | Версия, SHA коммита и checksum wheel |
| `work/setup/ray-pinned-macos-freeze.txt` | Установленные Python-пакеты |

Все эти файлы локальные и исключены из Git. Установленный пакет и сохранённый
wheel не требуют исходников из временного каталога для запуска. Временное
сборочное дерево нужно сохранять только для повторной сборки с кэшем.

Собирается Ray Core для Python. Опциями upstream отключены необязательный
отдельный C++ API (`RAY_DISABLE_EXTRA_CPP=1`) и Redis, предназначенный для
upstream-тестов (`RAY_BUILD_REDIS=0`). Java API и frontend dashboard не
собираются. Примеры проекта используют `include_dashboard=False`.

Для проверенного запуска использовались 6 параллельных заданий и лимит
ресурса памяти 24 576 MiB. По умолчанию скрипт задаёт 6 заданий и две трети
оперативной памяти машины. Это настройка планировщика Bazel, а не строгий
системный лимит памяти всех процессов.

## Происхождение версии

В исходном `python/ray/_version.py` SHA представлен placeholder
`{{RAY_COMMIT_SHA}}`. Перед упаковкой скрипт заменяет его на SHA, проверенный
через `git rev-parse HEAD`. Аналогичная операция выполняется в
[официальном скрипте упаковки Ray](https://github.com/ray-project/ray/blob/2ff4d94078ee94b3c9e6e4552ad84f78bad7f75f/ci/build/build-manylinux-wheel.sh).

Это единственная правка исходного дерева, использованная при успешной сборке.
Runtime-код Ray не исправлялся. Проверены исходная ревизия, список изменений,
содержимое метаданных внутри wheel и `ray.__commit__` установленного пакета.

Основа процедуры —
[официальная инструкция из назначенной ревизии](https://github.com/ray-project/ray/blob/2ff4d94078ee94b3c9e6e4552ad84f78bad7f75f/doc/source/ray-contribute/development.md).
Бинарник Bazel и его контрольная сумма опубликованы в
[релизе Bazel 7.5.0](https://github.com/bazelbuild/bazel/releases/tag/7.5.0).

## Фактически проверено 22 октября 2026

Получен локальный wheel:

```text
ray-3.0.0.dev0-cp312-cp312-macosx_15_0_arm64.whl
SHA-256: ea41d8545ea5b00cc0a4dd910cf00b06776a1fae36f5d4f39d381e77f9b42903
Размер: 34 090 892 байта
```

Это собственная сборка, не официальный распространяемый wheel. Тег данного
артефакта ограничивает установку CPython 3.12, macOS 15+ и arm64. Несмотря на
параметр компиляции `MACOSX_DEPLOYMENT_TARGET=12.0`, совместимость с более
старой macOS не проверена и не заявляется. На другой машине тег и checksum
повторно собранного пакета могут отличаться.

Bazel завершил 9 376 действий за 506.013 секунды. Это время основного build,
без настройки среды и последующей установки. Сначала процедура выполнена
по отдельным командам; публичный скрипт объединяет эти команды и добавляет
проверки путей/состояния. Для него проведена проверка синтаксиса `bash -n`;
повторная полная сборка именно через эту оболочку пока не запускалась.

Проверка установленной ревизии:

```bash
work/venvs/ray-pinned/bin/python -c \
  'import ray; print(ray.__version__, ray.__commit__)'
# 3.0.0.dev0 2ff4d94078ee94b3c9e6e4552ad84f78bad7f75f
```

На этой ревизии прошли все три существующих примера:

| Сценарий | Наблюдение |
|---|---|
| `examples/counter.py` | 100 операций → значение 100 |
| `examples/counter_restart.py` | 50 → падение → 0 → ещё 50; потеряно 50 подтверждённых прибавлений |
| `examples/counter_checkpoint.py` | 50 → падение → 50 → ещё 50; итог 100, потеряно 0 |

В обоих сценариях падения подтверждена смена PID актора. Три unit-теста
чтения/записи checkpoint прошли; `pip check` не выявил конфликтов.
Локальные JSON и логи этих запусков находятся в `runs/pinned-macos/`.

Команды для повторной проверки:

```bash
work/venvs/ray-pinned/bin/python examples/counter.py
work/venvs/ray-pinned/bin/python examples/counter_restart.py
work/venvs/ray-pinned/bin/python examples/counter_checkpoint.py
work/venvs/ray-pinned/bin/python -m unittest discover \
  -s tests -p test_counter_checkpoint.py -v
```

Эти проверки относятся к падению процесса актора на том же компьютере.
Потеря диска, узла и полное восстановление ML-приложения ими не проверяются.
