### 2. Счётчик и перезапуск актора

```bash
python examples/counter.py --output runs/review-counter.json
python examples/counter_restart.py --output runs/review-restart.json
python examples/counter_checkpoint.py --output runs/review-checkpoint.json
```

| Опыт | Ожидали | Получили | Отчёт |
| --- | --- | --- | --- |
| Без сбоя | 100 ответов, значение 100, отдельный PID | Совпало | [counter.json](../evidence/kt1/counter.json) |
| Restart | 50 → сбой → 0 → 50; потеря первых 50 прибавлений | Совпало, PID изменился | [counter-restart.json](../evidence/kt1/counter-restart.json) |
| Checkpoint после каждой операции | 50 → сбой → 50 → 100; потерь нет | Совпало, PID изменился, клиент проверил файл | [counter-checkpoint.json](../evidence/kt1/counter-checkpoint.json) |

Сбой вызывается через `os._exit(1)` после получения всех ответов первой группы.
Разрешён один рестарт, повторы изменяющих методов отключены. Чтение состояния
после сбоя повторяется с ожиданием до 60 секунд. Поэтому `passed` у restart
означает, что ожидаемая потеря состояния подтверждена.

В варианте с checkpoint перед ответом новое значение записывается в соседний
`state.tmp`, синхронизируется через `flush`/`fsync` и заменяет `state.json`
через `os.replace`. Новый процесс читает тот же файл
`runs/counter-checkpoint-<идентификатор>/state.json` с содержимым вида `{"value": 50}`.
Незавершённый временный файл игнорируется; повреждённый основной файл вызывает
ошибку. Итоговый JSON-отчёт клиента для восстановления не используется.

Проверено падение одного процесса при сохранном локальном диске.
`fsync` каталога не выполняется. Отказ питания, потеря диска, перенос на другой
узел и сбой между записью и доставкой ответа не проверялись; защиты от повторного
прибавления здесь нет. Основа примера — [checkpoint акторов Ray](https://docs.ray.io/en/latest/ray-core/fault_tolerance/actors.html#actor-checkpointing)
и [атомарная замена файла в Python](https://docs.python.org/3.12/library/os.html#os.replace).

### 3. Обучение на MNIST

```bash
python -m ray_ps.pilot --steps 20 --workers 2 --batch-size 32 --output runs/review-ps-01
python -m ray_ps.verify --run-dir runs/review-ps-01
python -m ray_ps.pilot --steps 20 --workers 2 --batch-size 32 --output runs/review-ps-02
python -m ray_ps.verify --run-dir runs/review-ps-02
```

Ожидали 20 шагов, 40 расчётов градиента, три отдельных актора и продвижение
каждого источника на 640 изображений. Веса и momentum должны совпасть
с последовательным эталоном при `atol=1e-6`, `rtol=1e-5`.

Оба запуска прошли проверку: число шагов и расчётов, версии и батчи совпали,
пропусков и дублей шагов нет. Максимальная абсолютная ошибка весов —
`5.960464477539063e-08`, momentum — `5.960464477539062e-07`.
Loss снизился примерно с 2.36 до 1.42 по батчам первого и последнего шага;
качество на test set не измеряли.

Сохранены [конфигурация](../evidence/kt1/ps-01/config.json),
[журнал](../evidence/kt1/ps-01/steps.jsonl), [состояние](../evidence/kt1/ps-01/final-state.pt)
и отчёты проверки [первого](../evidence/kt1/ps-01/verification.json)
и [второго](../evidence/kt1/ps-02/verification.json) запусков.
[Устройство пилота](../project.md#устройство-приложения).

После загрузки MNIST можно проверить сохранённый результат командой
`python -m ray_ps.verify --run-dir nis/evidence/kt1/ps-01 --data-root runs/data`.
Она перезапишет `verification.json` в этом каталоге.

### 4. Повторяемость и тесты проверки

```bash
python -m ray_ps.check_results --first runs/review-ps-01 --second runs/review-ps-02 --output runs/review-pilot-checks.json
python -m unittest discover -s tests -v
```

Ожидали совпадения тензоров в двух одинаковых запусках и отказа проверки,
если изменить один элемент momentum на 1. Оба условия выполнены: хеши весов
и momentum совпали, повреждённая копия отвергнута, старый `passed` в её отчёте
заменён на `failed`. Оригиналы не изменены. [Отчёт](../evidence/kt1/pilot-checks.json).

Все шесть unit-тестов прошли. Три проверяют файловый checkpoint: ошибки
`fsync`/`replace` сохраняют прежний файл, неполный временный файл игнорируется,
повреждённый основной файл отвергается. Ещё три проверяют пропуски и дубли
шагов, неверные батчи и переход эпох. Ошибки записи имитируются подменой
вызовов ОС. [Вывод тестов](../evidence/kt1/unit-tests.txt).


время отправления и ответа, запроса сбоя, готовности и первой операции

| --- | ---: | ---: |
| Итоговое значение | 8 | 16 |
| Потерянные подтверждённые прибавления | 8 | 0 |
| От запроса сбоя до первого подтверждения после рестарта, мс | 1985.60 | 1986.82 |
| p95 increment, мс | 0.375 | 1.884 |
| p99 increment, мс | 0.400 | 2.720 |

Журналы: [restart](../evidence/kt1/recovery-probe-restart.json)
и [checkpoint](../evidence/kt1/recovery-probe-checkpoint.json).
У каждой операции одна попытка, поэтому повторов здесь нет.

обучения этот сбор ещё не проверен.

В журналах обучения тоже есть время каждого шага. p95/p99 первого запуска —

включая холодный запуск процессов. Эти числа подтверждают возможность расчёта;
для сравнения скорости и оценки p99 нужна основная серия с прогревом.
