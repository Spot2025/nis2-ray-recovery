Wheel имеет тег CPython 3.12 / macOS 15+ / arm64. При сборке задавали

При повторной сборке тег и контрольная сумма могут измениться: версии части

### 2. Счётчик и перезапуск актора

```bash
python examples/counter.py --output runs/review-counter.json
python examples/counter_restart.py --output runs/review-restart.json
python examples/counter_checkpoint.py --output runs/review-checkpoint.json
```

| Опыт | Ожидали | Получили | Отчёт |
| --- | --- | --- | --- |
| Без сбоя | 100 ответов, значение 100, отдельный PID | Совпало | [counter.json](../evidence/kt1/counter.json) |
| Restart | 50 → сбой → 0 → 50; потеря первых 50 прибавлений | Совпало, PID изменился | [counter-restart.json](../evidence/kt1/counter-restart.json) |
| Checkpoint после каждой операции | 50 → сбой → 50 → 100; потерь нет | Совпало, PID изменился, клиент проверил файл | [counter-checkpoint.json](../evidence/kt1/counter-checkpoint.json) |

После получения всех ответов первой группы вызываем падение процесса
через `os._exit(1)`. Разрешён один рестарт; методы, меняющие состояние,
не повторяются. После сбоя повторяем чтение состояния с общим ожиданием
до 60 секунд. В опыте restart ожидаем потерю состояния: статус `passed`
означает, что результат совпал с этим ожиданием.

В варианте с checkpoint актор перед ответом записывает новое значение
в соседний файл `state.tmp`, вызывает `flush`/`fsync`, затем заменяет `state.json`
через `os.replace`. После перезапуска он читает тот же файл
`runs/counter-checkpoint-<идентификатор>/state.json` с содержимым вида `{"value": 50}`.
Незавершённый временный файл при чтении пропускается. Если повреждён основной
файл, программа сообщает об ошибке. Итоговый JSON-отчёт клиента
для восстановления не используется.

Проверили падение одного процесса при сохранном локальном диске.
`fsync` каталога не выполняется. Отказ питания, потеря диска, перенос на другой
узел и сбой между записью и доставкой ответа не проверялись; защиты от повторного
прибавления здесь нет. Основа примера — [checkpoint акторов Ray](https://docs.ray.io/en/latest/ray-core/fault_tolerance/actors.html#actor-checkpointing)
и [атомарная замена файла в Python](https://docs.python.org/3.12/library/os.html#os.replace).

### 3. Обучение на MNIST

```bash
python -m ray_ps.pilot --steps 20 --workers 2 --batch-size 32 --output runs/review-ps-01
python -m ray_ps.verify --run-dir runs/review-ps-01
python -m ray_ps.pilot --steps 20 --workers 2 --batch-size 32 --output runs/review-ps-02
python -m ray_ps.verify --run-dir runs/review-ps-02
```

В каждом запуске ожидали 20 шагов, 40 расчётов градиента и три отдельных актора.
Каждый источник должен был продвинуться на 640 изображений, а веса и momentum —
совпасть с последовательным эталоном при `atol=1e-6`, `rtol=1e-5`.

Оба запуска прошли проверку: число шагов и расчётов, версии и батчи совпали,
пропусков и дублей шагов нет. Максимальная абсолютная ошибка весов —
`5.960464477539063e-08`, momentum — `5.960464477539062e-07`.
Loss снизился примерно с 2.36 до 1.42 по батчам первого и последнего шага;
качество на test set не измеряли.

Сохранили [конфигурацию](../evidence/kt1/ps-01/config.json),
[журнал](../evidence/kt1/ps-01/steps.jsonl), [состояние](../evidence/kt1/ps-01/final-state.pt)
и отчёты проверки [первого](../evidence/kt1/ps-01/verification.json)
и [второго](../evidence/kt1/ps-02/verification.json) запусков.
[Устройство пилота](../project.md#устройство-приложения).

После загрузки MNIST можно проверить сохранённый результат командой
`python -m ray_ps.verify --run-dir nis/evidence/kt1/ps-01 --data-root runs/data`.
Она перезапишет `verification.json` в этом каталоге.

### 4. Повторяемость и тесты проверки

```bash
python -m ray_ps.check_results --first runs/review-ps-01 --second runs/review-ps-02 --output runs/review-pilot-checks.json
python -m unittest discover -s tests -v
```

Проверили, что одинаковые запуски дают одинаковые тензоры: хеши весов
и momentum совпали. Затем в копии результата увеличили один элемент momentum
на 1. Проверка обнаружила ошибку и заменила прежний статус `passed`
на `failed`. Исходные результаты сохранились без изменений.
[Отчёт](../evidence/kt1/pilot-checks.json).

Все шесть unit-тестов прошли. Три из них проверяют файловый checkpoint:
при ошибках `fsync`/`replace` прежний файл остаётся целым, неполный временный
файл не используется, а повреждение основного файла вызывает ошибку.
Ещё три проверяют пропуски и дубли шагов, неверные батчи и переход между эпохами.
Ошибки записи имитировали подменой вызовов ОС.
[Вывод тестов](../evidence/kt1/unit-tests.txt).

### 5. Данные для метрик

```bash
python -m examples.recovery_probe --mode restart --output runs/review-probe-restart.json
python -m examples.recovery_probe --mode checkpoint --output runs/review-probe-checkpoint.json
```

Для пробного замера выполнили 8 прибавлений до сбоя и 8 после него.
В журнал записали ID операций и попыток, PID и состояние. Также отметили время
отправления запросов и получения ответов, запроса сбоя, готовности актора
и первой операции после рестарта. По этим данным рассчитали время
восстановления, задержки и потери:

| Показатель | Restart | Checkpoint |
| --- | ---: | ---: |
| Итоговое значение | 8 | 16 |
| Потерянные подтверждённые прибавления | 8 | 0 |
| От запроса сбоя до первого подтверждения после рестарта, мс | 1985.60 | 1986.82 |
| p95 increment, мс | 0.375 | 1.884 |
| p99 increment, мс | 0.400 | 2.720 |

Журналы: [restart](../evidence/kt1/recovery-probe-restart.json)
и [checkpoint](../evidence/kt1/recovery-probe-checkpoint.json).
У каждой операции в этих запусках одна попытка.
Как учитывать повторные расчёты градиента и replay, показали
в [плане](../experiment-plan.md#метрики) на примере будущего журнала
и расчёта счётчиков. При реальных отказах обучения сбор этих данных
ещё не проверяли.

В журналах обучения тоже есть время каждого шага. p95/p99 первого запуска —
97.67/1437.64 мс, второго — 84.75/1246.37 мс. В выборку входят все 20 шагов,
включая холодный запуск процессов. Для сравнения производительности
проведём серии по 1000 шагов после прогрева.
