# Описание проекта

[Задание P25-B «Ray: акторы и восстановление»](https://distsys.ru/osukhoroslov/nis2/src/branch/main/project-tasks/p25-b-ray-actors-recovery.md).
Команда №10: Зодоров Адам, Царапкин Максим, Шиляев Иван.
Основная статья — [Ray: A Distributed Framework for Emerging AI Applications, OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/moritz).

## Задача

Хотим проверить, какое состояние нужно сохранять, чтобы обучение нейросети
продолжилось после падения процесса. Кроме весов модели есть momentum
оптимизатора, номер шага и позиции в данных. Если восстановить их несогласованно,
программа может продолжить работу, но получить неверный результат.

Используем Ray как готовую среду выполнения — это путь с авторским артефактом
из задания. Версия закреплена коммитом `2ff4d94078ee94b3c9e6e4552ad84f78bad7f75f`.
На Ray напишем приложение с несколькими акторами, два способа продолжения
после сбоя, журнал операций и проверки. Для сравнения сделаем то же приложение
на `multiprocessing` и очередях.

Нагрузка — синхронное обучение небольшой ConvNet на MNIST. За основу взят
[пример parameter server из Ray](https://github.com/ray-project/ray/blob/2ff4d94078ee94b3c9e6e4552ad84f78bad7f75f/doc/source/ray-core/examples/plot_parameter_server.ipynb).
К нему добавлены отдельные источники данных, SGD с momentum, фиксированный
порядок батчей, ID шагов, журнал и последовательный эталон.
PyTorch считает градиенты, torchvision загружает данные.
[Источники и лицензии](../README.md#источники-и-лицензии).

## Устройство приложения

```mermaid
flowchart LR
    S1["DataShard 0"] --> W1["Задача градиента 0"]
    S2["DataShard 1"] --> W2["Задача градиента 1"]
    W1 --> PS["ParameterServer"]
    W2 --> PS
    PS -. "Веса следующего шага" .-> W1
    PS -. "Веса следующего шага" .-> W2
```

`DataShard` — актор, который хранит позицию в своей части MNIST и текущий
батч. `ParameterServer` хранит веса, momentum и номер применённого шага.
Градиенты считают обычные Ray-задачи. Координатор запускает шаги и пишет журнал;
позже он будет вызывать сбои в заданных точках.

Один шаг устроен так:

1. `DataShard.reserve(step)` выбирает и резервирует индексы изображений.
2. Координатор кладёт текущие веса в объектное хранилище через `ray.put`.
3. Задачи `compute_gradient` читают батчи у источников и считают градиенты
   на одной версии весов.
4. `ParameterServer.apply` проверяет номера шагов и источников, усредняет
   градиенты в порядке номеров shard и выполняет шаг SGD с momentum.
5. `DataShard.commit(step)` продвигает позиции данных. Координатор записывает
   батчи, версии, время шага и хеш новых весов.

Следующий шаг начинается после завершения предыдущего. По умолчанию работают
два вычислителя с батчами по 32 изображения. В каждом процессе PyTorch
использует один CPU-поток; seed задан явно.

Пилот пока работает без сбоев: рестарты акторов и повторы задач отключены.
Повтор текущего `reserve`/`commit` обрабатывается только пока жив процесс.
`apply` отвергает неожиданный номер шага. Обработку повторов после восстановления
ещё нужно добавить.

## Сбои и восстановление

Сравним две стратегии:

- **Restart:** Ray запускает процесс заново, прикладное состояние сбрасывается.
- **Checkpoint/replay:** процесс загружает снимок состояния и применяет
  обновления из журнала, записанные после снимка.

Проверим работу без сбоев и три вида отказов: вычислительная задача падает
во время расчёта градиента; сервер модели — после подтверждённого шага;
источник данных — с зарезервированным, но ещё не подтверждённым батчем.
Под отказом worker здесь понимаем падение процесса обычной задачи,
чтобы отдельно проверить поведение задач и акторов Ray.

В снимок должны входить веса, momentum, номер шага, прогресс источников,
незавершённые батчи и сведения об уже применённых запросах. В журнал планируем
писать усреднённый градиент, ID шага, базовую версию модели и ID батчей.
Подтверждать обновление будем после записи журнала на диск. При replay
это позволит восстановить обновление без нового расчёта градиентов.

Отдельно проверим случай, когда сервер применил шаг, но упал до отправки
ответа. Клиент повторит запрос с тем же ID; сервер должен распознать его
и не менять модель второй раз. Источники должны согласовать с этим свой
прогресс. Одних независимых снимков акторов для этого недостаточно:
нужно восстановить состояние незавершённого шага по журналам.
Этот протокол ещё предстоит реализовать и проверить.

## Что должно получиться

| Результат | Как проверим |
| --- | --- |
| Приложение из нескольких акторов и задач | Отдельные PID, согласованные версии модели и позиции источников в журнале |
| Restart и checkpoint/replay | Перезапуск процесса; сравнение восстановленного состояния с эталоном, учёт потерь |
| Управляемые отказы задачи, сервера и источника | Известная точка сбоя, PID до/после, журнал попыток и первый правильный шаг после восстановления |
| Журнал и защита от двойного применения | ID операций и попыток, хеши состояния; проверки пропусков, дублей и потерянного ответа |
| Вариант на обычных процессах (baseline) | Те же данные, алгоритм обучения, правила сохранения и ресурсы, что у Ray |
| Независимая проверка | Точное сравнение ID и прогресса, сравнение весов и momentum с допуском; намеренно испорченный результат должен быть отвергнут |
| Эксперименты и разбор результатов | Не менее трёх серий с повторами, сырые журналы, скрипт обработки, таблицы и графики восстановления, задержек и повторной работы |

## Упрощения

Все процессы работают на одном компьютере, на CPU. В одном запуске вызываем
один отказ. Координатор, Ray head/GCS и локальный диск продолжают работать;
перезапущенный процесс читает тот же диск. Отказы машины, питания и диска,
сетевые разделения и несколько одновременных отказов в основной план не входят.

Обучение синхронное, порядок данных и агрегации фиксирован. Численные результаты
сравниваем в одной среде с заранее выбранным допуском: одинаковый seed
не гарантирует одинаковые байты на разных платформах. Loss используем
для наблюдения за обучением, а правильность проверяем по полному состоянию.

Такой опыт покажет поведение выбранного приложения при локальных сбоях.
Результаты не будут описывать отказоустойчивость большого кластера Ray
или воспроизводить масштаб RL-экспериментов из статьи. Обязательный объём
задания при этих упрощениях сохраняется.
