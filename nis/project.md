# Описание проекта

[Задание P25-B «Ray: акторы и восстановление»](https://distsys.ru/osukhoroslov/nis2/src/branch/main/project-tasks/p25-b-ray-actors-recovery.md).
Команда №10: Зодоров Адам, Царапкин Максим, Шиляев Иван.
Основная статья — [Ray: A Distributed Framework for Emerging AI Applications, OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/moritz).

## Задача

После перезапуска части приложения могут оказаться на разных шагах обучения:
например, веса уже обновлены, а позиция в данных осталась от прошлого шага.
Поэтому проверим, как согласованно восстанавливать веса, momentum оптимизатора,
номер шага и позиции источников данных.

Выбрали путь с авторским артефактом и используем Ray
[назначенного коммита](checkpoints/01.md#ресурсы). Уже собрали приложение
из акторов и задач: оно обучает модель без сбоев, записывает шаги в журнал
и позволяет проверить результат. Дальше добавим два способа восстановления
и реализуем то же приложение на `multiprocessing` с очередями для сравнения с Ray.

В качестве нагрузки выбрали синхронное обучение небольшой ConvNet на MNIST.
За основу взяли
[пример parameter server из Ray](https://github.com/ray-project/ray/blob/2ff4d94078ee94b3c9e6e4552ad84f78bad7f75f/doc/source/ray-core/examples/plot_parameter_server.ipynb).
Добавили отдельные источники данных, SGD с momentum, фиксированный
порядок батчей, ID шагов, журнал и последовательный эталон.
PyTorch считает градиенты, torchvision загружает данные.
[Источники и лицензии](../README.md#источники-и-лицензии).

## Устройство приложения

```mermaid
flowchart LR
    S1["DataShard 0"] --> W1["Задача градиента 0"]
    S2["DataShard 1"] --> W2["Задача градиента 1"]
    W1 --> PS["ParameterServer"]
    W2 --> PS
    PS -. "Веса следующего шага" .-> W1
    PS -. "Веса следующего шага" .-> W2
```

`DataShard` — актор, который хранит позицию в своей части MNIST и текущий
батч. `ParameterServer` хранит веса, momentum и номер применённого шага.
Градиенты считают обычные Ray-задачи. Координатор запускает шаги и пишет журнал.
В координатор также добавим возможность вызывать сбои в заданных точках.

Один шаг устроен так:

1. `DataShard.reserve(step)` выбирает и резервирует индексы изображений.
2. Координатор кладёт текущие веса в объектное хранилище через `ray.put`.
3. Задачи `compute_gradient` читают батчи у источников и считают градиенты
   на одной версии весов.
4. `ParameterServer.apply` проверяет номера шагов и источников, усредняет
   градиенты в порядке номеров shard и выполняет шаг SGD с momentum.
5. `DataShard.commit(step)` продвигает позиции данных. Координатор записывает
   батчи, версии, время шага и хеш новых весов.

Следующий шаг начинается после завершения предыдущего. По умолчанию работают
два вычислителя с батчами по 32 изображения. В каждом процессе PyTorch
использует один CPU-поток; seed задан явно.

В пилоте рестарты акторов и повторы задач отключены. Пока процесс работает,
он обрабатывает повторные вызовы текущего `reserve`/`commit`, а `apply`
отвергает неожиданный номер шага. После восстановления эта обработка
пока не реализована.

## Файлы запуска

| Файл результата | Содержимое |
| --- | --- |
| `config.json` | Параметры, версии, seed, хеши данных и исходников |
| `steps.jsonl` | Батчи, номера шагов и версий модели, позиции источников, время и хеши весов |
| `summary.json` | Итог запуска и p95/p99 времени шага |
| `final-state.pt` | Веса, momentum, номер шага и позиции источников |
| `verification.json` | Результат проверки по последовательному эталону |

Статус `completed_pending_independent_verification` в `summary.json` означает
завершение программы. Результат отдельной проверки находится в `verification.json`:
`verify` перезаписывает этот файл и при успехе, и при ошибке.
`check_results` сравнивает два запуска, а затем намеренно повреждает momentum
в копии результата и проверяет, что ошибка обнаружена. Исходные результаты
при этом не меняются.

## Сбои и восстановление

Сравним две стратегии:

- **Restart:** Ray запускает процесс заново, прикладное состояние сбрасывается.
- **Checkpoint/replay:** процесс загружает снимок состояния и применяет
  обновления из журнала, записанные после снимка.

Сначала проверим работу без сбоев, затем три вида отказов. Вычислительную
задачу прервём во время расчёта градиента, сервер модели — после подтверждённого
шага, а источник данных — когда батч уже зарезервирован, но ещё не подтверждён.
Под worker здесь понимаем процесс обычной Ray-задачи.

В checkpoint будем сохранять веса, momentum, номер шага, прогресс источников,
незавершённые батчи и уже применённые запросы. В журнал будем записывать
усреднённый градиент, ID шага, базовую версию модели и ID батчей.
Подтверждение отправим после записи журнала на диск. Сохранённый градиент
позволит при replay применить обновление без повторного расчёта градиентов.

Отдельно проверим потерю ответа: сервер применил шаг, но упал до отправки
ответа. Клиент повторит запрос с тем же ID, а сервер должен вернуть прежний
результат без повторного применения. Позиции источников должны соответствовать
этому шагу. Незавершённый шаг восстановим по журналам сервера и источников.

## Что должно получиться

| Результат | Как проверим |
| --- | --- |
| Приложение из нескольких акторов и задач | Проверим отдельные PID и согласованность версий модели и позиций источников в журнале |
| Restart и checkpoint/replay | Перезапустим процесс, сравним восстановленное состояние с эталоном и посчитаем потери |
| Управляемые отказы задачи, сервера и источника | Запишем точку сбоя, PID до и после него, попытки выполнения и первый правильный шаг после восстановления |
| Журнал и защита от двойного применения | По ID операций и попыток и хешам состояния проверим пропуски и дубли, в том числе при потере ответа |
| Вариант на обычных процессах (baseline) | Те же данные, алгоритм обучения, правила сохранения и ресурсы, что у Ray |
| Независимая проверка | Сравним ID и прогресс точно, а веса и momentum — с допуском. Убедимся, что проверка отвергает намеренно испорченный результат |
| Эксперименты и разбор результатов | Проведём не менее трёх серий с повторами. Сохраним сырые журналы, скрипт обработки, таблицы и графики восстановления, задержек и повторной работы |

Конфигурации и метрики описаны в [плане эксперимента](experiment-plan.md).

## Упрощения

Работаем на одной машине и только на CPU. В каждом запуске со сбоем вызываем
один отказ процесса. Предполагаем, что координатор, Ray head/GCS и локальный
диск продолжают работать, а новый процесс читает тот же диск. Отказы машины,
питания и диска, сетевые
разделения и одновременные отказы нескольких процессов в основной план не входят.

Обучение синхронное, порядок данных и агрегации фиксирован. Численные результаты
сравниваем в одной среде с заранее выбранным допуском. Loss используем
для наблюдения за обучением, а правильность проверяем по полному состоянию.

Результаты позволят сравнить способы восстановления нашего приложения
после отказа отдельного процесса на одной машине.
