# План эксперимента

## Проверяемый вопрос

Какие прикладные состояния и сведения об операциях должны пережить сбой,
чтобы локальное обучение с parameter server продолжилось корректно?
Как частота checkpoint влияет на время восстановления, задержки шагов
и повторную работу по сравнению с restart и процессным baseline?

Гипотезы для проверки: перезапуск процесса без сохранения не восстанавливает
обучение; snapshot с журналом может сохранить подтверждённые эффекты,
если восстановлены также momentum и прогресс данных; уменьшение интервала
checkpoint может сократить replay, увеличив цену работы без сбоев.
Это ожидаемые зависимости, а не уже полученные выводы.

## Сравниваемые варианты и baseline

| Вариант | Runtime | Политика состояния |
| --- | --- | --- |
| R0 | Ray назначенного SHA | Перезапуск с повторной инициализацией, без восстановления внешнего состояния |
| R1 | Тот же Ray | Периодический checkpoint и журнал агрегированных обновлений, replay, распознавание повторов |
| P0 | Python multiprocessing + очереди | Та же политика, что R0 |
| P1 | Python multiprocessing + очереди | Та же политика, что R1 |

P0/P1 — простой процессный baseline из задания. Последовательная программа
проверки — отдельный эталон правильности; её время не выдаём за производительность
распределённого baseline. Реализация P0/P1 к КТ1 не требуется.

Одинаковыми остаются данные, начальные веса, оптимизатор, порядок и размер
батчей, правило усреднения, число вычислителей, точки сбоев, содержимое
checkpoint/журнала и правило подтверждения после записи. Число CPU-потоков
PyTorch — один в каждом процессе; GPU не используется. Журнал наблюдений
координатора не служит скрытым источником восстановления для R0/P0.

R0/P0 после перезапуска сбрасывают затронутое состояние. Политику продолжения
фиксируем при реализации: если номер версии не позволяет безопасно продолжить,
регистрируем отказ продолжения и потерю состояния. Неверный результат нельзя
принимать как корректный только потому, что процесс снова отвечает.

## Данные или нагрузки

MNIST train: 60 000 изображений 28×28 и метки 0–9, загружаемые torchvision.
Исходные данные сохраняются в `runs/data/`, их контрольная сумма — в отчёте.
Для исходного пилота используется ConvNet из [описания проекта](project.md),
SGD с `lr=0.01`, `momentum=0.9`, `seed=2026`.

При W источниках shard j содержит исходные индексы j, j+W, j+2W, … .
Для каждой эпохи порядок задаёт `torch.randperm` с генератором
`seed + 1009*j + 1000003*epoch`. Батчи могут пересекать границу эпохи,
каждый имеет фиксированный размер. Идентификатор — `(step, shard)`;
в журнале есть исходные индексы. Начальный seed модели и набор данных одинаковы
во всех сравниваемых запусках конфигурации.

Логическая операция — один глобальный шаг SGD по W батчам. Повторная попытка
вычисления и повторное применение обновления — разные события. Успех шага
восстановленного обучения требует корректных весов, состояния оптимизатора
и подтверждения соответствующих батчей источниками.

## Конфигурации и план запусков

Среда: [environment.md](environment.md), Python 3.12, Ray
`2ff4d94078ee94b3c9e6e4552ad84f78bad7f75f`, зависимости зафиксированы.
Машина подготовки: Apple Silicon, 12 ядер, 36 ГиБ RAM. Исходный пилот
использует 2 вычислителя, 2 источника и 1 сервер. Ray резервирует 3 логических
CPU: по одному для задач и сервера; источники выполняют короткие операции
без отдельной CPU-резервации. Резервация Ray не является квотой ОС.

Начальная основная конфигурация: W=2, батч=32 на вычислитель, K=10 шагов
между snapshots, 1000 измеряемых шагов после 50 шагов прогрева.
Прогрев продвигает модель и источники одинаково во всех вариантах, его
задержки исключаются из основной выборки, но сохраняются в сырых данных.
Для отказа после прогрева фиксируем логическую точку около 500-го измеряемого
шага и конкретную фазу. Сбой при неопределённом ответе — отдельная проверка
правильности вне таблицы измерительных серий, не смесь с отказом между
полностью подтверждёнными шагами.

| Серия | Условия |
| --- | --- |
| A | Без сбоев: R0, R1, P0, P1 |
| B | Отказ одного обычного вычислителя во время расчёта заданного шага: те же варианты |
| C1 | Отказ сервера модели после подтверждения заданного шага: те же варианты; число обновлений после последнего snapshot явно записывается |
| C2 | Отказ источника с зарезервированным батчем: те же варианты |

Для C1 выбираем шаг 505 измеряемого участка: при K=1 snapshot уже свежий,
при K=10/50 после предыдущего snapshot остаётся пять обновлений для replay
(границы K отсчитываются от начала измеряемого участка). Это часть исследуемого
компромисса, а не одинаковый объём replay для разных K.

По три независимых запуска каждой конфигурации, с новым состоянием и каталогом
результатов. Это 48 запусков основной матрицы. Порядок вариантов внутри
блоков повторов перемешивается с сохранённым seed; запуски идут последовательно.
Фоновые сборки и другие тяжёлые задачи на машине на время основной серии
останавливаются. Состояние кэша данных и режим питания фиксируются в отчёте.

Дополнительные срезы, без полного декартова перебора:

- K=1 и K=50 для R1/P1 в A/C1, прочие параметры исходные: ещё 24 запуска.
- Отдельно W=4 при батче 32 и отдельно батч=128 при W=2, K=10,
  R1/P1 в A/C1: ещё 24 запуска.

Итого исходный план — 96 запусков, три повтора на конфигурацию. Перед КТ2
выполним пилот длительности и памяти: если выборка или время работы
недостаточны, изменим число шагов/диапазон с объяснением в этом файле до
основных измерений. Маленький пилот КТ1 доказывает доступность данных;
его p99 не интерпретируем как устойчивую оценку хвоста распределения.

## Метрики

Все интервалы end-to-end измеряет координатор одним монотонным таймером.
Часы разных процессов не вычитаем друг из друга. Длительность вычисления
внутри worker — отдельный интервал на его собственном таймере.

| Метрика | Определение, единицы и сбор |
| --- | --- |
| Время восстановления | мс от запроса инъекции сбоя до первого корректного подтверждения полезного шага после него; отдельно время готовности процесса. Если корректное продолжение невозможно, это не нулевая задержка: фиксируем неуспех/таймаут |
| p95/p99 шага | мс от первого отправления логической операции до её окончательного подтверждения, включая ожидание и повторы; линейный эмпирический квантиль по шагам после прогрева |
| Производительность | число корректно подтверждённых полезных шагов / длительность измеряемого участка, шаг/с; повторные попытки не увеличивают числитель |
| Потери | число подтверждённых ID, эффект которых отсутствует в восстановленном результате, шт.; проверяется по журналам и эталону, а не только loss |
| Двойное применение | число применений сверх одного на логический ID, шт.; повторная доставка без второго эффекта дублем применения не считается |
| Повторная работа | число повторных gradient attempts, выполненных backward и обновлений при replay, раздельно; также их суммарное CPU/wall время, если доступно |
| Стоимость сохранения | байты записанных journals/snapshots и длительность записи/публикации, байт и мс |
| Корректность | точные ID/версии/позиции и максимальная абсолютная ошибка весов и momentum; pass/fail по выбранному допуску |
| Прикладной ход обучения | loss на батчах, вспомогательно; не критерий восстановления |

Данные пилота: `ray_ps.pilot` пишет `config.json`, `steps.jsonl`,
`summary.json`, `final-state.pt`; `ray_ps.verify` — `verification.json`.
`examples.recovery_probe` записывает времена запроса сбоя, наблюдения ошибки,
готовности и первой операции после перезапуска, ID попыток и наблюдаемые состояния.
В этом счётчике задержка increment исключает ожидание готовности; в основном
приложении end-to-end шаг, затронутый сбоем, будет включать это ожидание.
Нулевые повторы в пилоте не являются проверкой повторной работы при отказе worker.
Попытки, прерванные гибелью процесса, отмечаются как незавершённые. Если
их точное процессорное время неизвестно, не подменяем его нулём: отдельно
показываем количество попыток и границы доступной оценки выполненной работы.

## Проверка корректности

Пилот проверяется отдельной программой: она заново строит порядок входов
по конфигурации, отвергает пропущенные/повторные шаги и неверные батчи,
объединяет W батчей и делает один последовательный backward. Она не вызывает
исследуемые actor/worker, их агрегацию и будущий код восстановления.
Определение ConvNet и PyTorch общие; это явная граница независимости.

Сравниваются все веса, momentum и позиции источников. Первоначальные допуски
`atol=1e-6`, `rtol=1e-5` проверяются на пилоте в одной среде. В основной
серии допуск фиксируется до запуска; нельзя расширять его лишь ради прохождения
неудачного опыта. Хеши канонических тензоров позволяют дополнительно проверить
повторяемость одинаковых запусков. Для численно эквивалентной разной агрегации
равенство хешей не требуется.

После реализации восстановления проверка будет учитывать неопределённые
исходы вызовов, повторные попытки и связи reserve → model update → commit.
Проверка ID и шагов дополняет численный эталон, поскольку один loss не
различает пропуск, двойной эффект или неверный порядок.

## Обработка и анализ

Сохраняем сырые события каждого запуска, версии, параметры, seed, конфигурацию
сбоя и исход проверки. Сначала проверяем корректность, затем сравниваем стоимость.
Ошибочные запуски и таймауты показываем отдельно; не удаляем их из отчёта
и не выдаём их быстрые ответы за успешное восстановление.

Считаем показатели каждого запуска отдельно; для трёх повторов показываем
все точки, медиану и min/max. Не объединяем все шаги трёх запусков в одну
выборку, скрывающую разброс между запусками. Для p99 показываем размер выборки.
Основные графики: восстановление против K, p95/p99 без отказа и при отказе,
повторная работа и объём записи против K; таблица корректности всех вариантов.

Текущие команды проверки и пилота приведены в [КТ1](checkpoints/01.md).
Общий обработчик серий и графиков будет добавлен вместе с реализацией baseline;
к КТ1 полного экспериментального результата не заявляем.
