## Что уже есть

Первый учебный пример: один актор Ray хранит счётчик и выполняет 100 команд
«прибавить 1». Программа проверяет начальное значение, результат каждой операции,
итоговое значение и выполнение актора в отдельном процессе.

Состояние счётчика хранится в памяти процесса актора. Пример проверяет
запуск Ray и работу актора без сбоев.

Второй пример вызывает падение процесса актора и проверяет его автоматический
перезапуск. После перезапуска счётчик начинается с нуля: сохранения состояния
в этом примере нет.

Третий пример сохраняет значение в файл после каждого прибавления и читает
его в конструкторе. После падения процесса счётчик продолжает с прежнего значения.

## Первый запуск

Нужен Python 3.12. Все команды выполняются в корне этого репозитория.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python examples/counter.py
```

Ожидаемый вывод, помимо служебных сообщений Ray:

```text
Отправлено операций: 100
Ожидаемое значение: 100
Полученное значение: 100
Проверка пройдена: актор выполнил все операции в отдельном процессе.
Результат сохранён: runs/counter.json
```

Можно изменить число операций и место сохранения результата:

```bash
python examples/counter.py --increments 250 --output runs/counter-250.json
```

Каталог `runs/` исключён из Git. Проверенные свидетельства этапов сохраняем
отдельно в `nis/evidence/`.

## Как читать первый пример

- `@ray.remote` превращает класс `Counter` в актор.
- `Counter.remote()` создаёт актор в отдельном процессе.
- `counter.increment.remote()` отправляет ему команду.
- `ray.get(...)` ожидает результаты.
- Все вызовы поступают от одного клиента одному обычному синхронному актору.
- `max_restarts=0` и `max_task_retries=0` явно отключают перезапуски и повторы
  для этого примера.
- `ray.shutdown()` отключает клиент и завершает созданный им локальный Ray.

## Падение и перезапуск актора

В подготовленном окружении:

```bash
python examples/counter_restart.py
```

Сценарий выполняет 50 прибавлений и получает все ответы, затем завершает процесс
актора через `os._exit(1)`. Ray создаёт новый процесс и повторно вызывает
`__init__`: значение становится 0. После ещё 50 прибавлений итог равен 50.
Клиент получил подтверждения 100 операций, но результат первых 50 утрачен.

Ожидаемый вывод, помимо служебных сообщений Ray (PID будут другими):

```text
До падения: 50; PID: 9067
Вызываем падение процесса актора...
Падение подтверждено: ActorUnavailableError
После перезапуска: 0; PID: 9070
После ещё 50 операций: 50
Всего подтверждено прибавлений: 100
Потеряно в состоянии после сбоя: 50
Проверка пройдена: процесс перезапущен, прежнее состояние потеряно.
Результат сохранён: runs/counter-restart.json
```

Ray также выводит сообщение о гибели worker: это ожидаемое следствие
вызванного сбоя. Конкретный подкласс `RayActorError` может зависеть от момента
обнаружения сбоя; в сохранённых запусках получен `ActorUnavailableError`.

- `max_restarts=1` разрешает один перезапуск актора.
- `max_task_retries=0` отключает повторы методов, включая команду падения.
- Только чтение состояния после сбоя использует `max_task_retries=-1`:
  его можно повторять, пока актор перезапускается. Клиент ждёт не более 60 секунд.
- Прежний handle `counter` используется и после перезапуска.
- Проверки сверяют ответы на операции, значения счётчика и смену PID.

Числа операций можно задать отдельно:

```bash
python examples/counter_restart.py --before-crash 7 --after-restart 3
```

Здесь ожидается `7 → падение → 0 → 3`: из 10 подтверждённых прибавлений
результат 7 потерян. Статус `passed` означает, что проверка подтвердила
ожидаемую потерю состояния, а не сохранность данных при сбое.
JSON в `runs/` — отчёт запуска; актор его не читает для восстановления.

## Восстановление из файла

```bash
python examples/counter_checkpoint.py
python examples/counter_checkpoint.py --before-crash 7 --after-restart 3
```

`counter_checkpoint.py` использует те же настройки перезапуска и тот же сбой
через `os._exit(1)`. Теперь `increment()` сначала сохраняет новое значение
в checkpoint, затем меняет значение в памяти и возвращает ответ.
При перезапуске конструктор загружает checkpoint.

| Этап при 50 операциях до сбоя и 50 после | Без сохранения | С checkpoint |
| --- | ---: | ---: |
| Перед падением | 50 | 50 |
| Сразу после перезапуска | 0 | 50 |
| После следующих 50 операций | 50 | 100 |
| Подтверждённых прибавлений потеряно в состоянии | 50 | 0 |

Путь к checkpoint печатается в начале запуска:
`runs/counter-checkpoint-<идентификатор>/state.json`.
Формат — `{"value": 50}`. Новый запуск всей программы создаёт отдельный каталог
и начинает опыт с нуля. При рестарте актора внутри опыта используется прежний
абсолютный путь; файл сохраняется и после завершения программы.

Запись идёт в соседний `state.tmp`: `flush()` и `os.fsync()` завершают запись
буферов, затем `os.replace()` атомарно заменяет `state.json`.
Неоконченный временный файл не используется при восстановлении.
Если основной checkpoint повреждён, загрузка завершается ошибкой.

`runs/counter-checkpoint.json` — отдельный итоговый отчёт. Он содержит
результаты проверок, путь к checkpoint и значения, прочитанные клиентом из файла
перед сбоем, после перезапуска и в конце опыта. Сам отчёт актор не загружает.
Воспроизводимые команды и сохранённые результаты — в [технических материалах](nis/README.md).

Сценарий проверяет гибель одного процесса на той же машине после получения
ответов на первую группу операций. Локальный файл должен оставаться доступным.
Сбой машины, потеря диска и перенос актора на другой узел не проверены.
Сбой между записью и доставкой ответа также не исследуется: такая операция
может сохраниться без подтверждения клиенту. Защита от повторного прибавления
при повторе такого запроса здесь не реализована; повторы `increment()` отключены.

Основание: [checkpoint и восстановление акторов Ray](https://docs.ray.io/en/latest/ray-core/fault_tolerance/actors.html#actor-checkpointing),
[атомарная замена файла в Python](https://docs.python.org/3.12/library/os.html#os.replace).

## Проверки работы с checkpoint

```bash
python -m unittest discover -s tests -v
```

Три теста без запуска кластера проверяют: сохранность прежнего checkpoint
при ошибках `fsync` и `replace`, игнорирование неполного временного файла
и отказ от загрузки повреждённого основного файла.
